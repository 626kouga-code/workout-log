# 運用（監視・バックアップ）

[目次に戻る](README.md)

AWS の環境は動作確認・発表のときだけ作るため、運用もその間に必要なものに絞る。

## ログ

- アプリは、ログを JSON 形式で標準出力に出す。ECS Express Mode の設定で、CloudWatch Logs に集める（保存期間は 7 日）
- 1 リクエストにつき 1 行のアクセスログを出す：時刻、リクエスト ID、ユーザー ID（ログイン時）、メソッド、パス、ステータス、処理時間
- エラーは、エラーの内容とスタックトレースを、リクエスト ID と一緒に出す
- **出さないもの**：パスワード、セッショントークン、メール確認のトークン、メールアドレス、体重などの記録の中身

| レベル | 出すもの |
| --- | --- |
| ERROR | 想定外の例外、外部サービス（S3・SES）の呼び出しの失敗 |
| WARN | 想定内だが注意が必要なもの（同期の競合で変更を捨てた、メールの送信に失敗して再送待ち） |
| INFO | アクセスログ、ユーザー登録・退会、ワークアウトの同期の件数 |

## 監視・エラー通知

CloudWatch アラームを置き、条件を満たしたら Amazon SNS（通知サービス）から開発者にメールで知らせる。

| 監視対象 | 条件（目安） | 想定する原因 |
| --- | --- | --- |
| ALB の 5xx 応答 | 5 分間に 10 件以上 | アプリのエラー、DB に接続できない |
| ECS のタスク | 動いているタスクが 0 になった | 起動に失敗し続けている（設定・秘密情報の誤り） |
| アプリの ERROR ログ | 5 分間に 5 件以上（メトリクスフィルタで数える） | 想定外の例外 |
| RDS の CPU 使用率 | 80% 以上が 10 分続く | 重いクエリ（集計など） |
| RDS の空き容量 | 2GB 未満 | データ・ログの増加 |

### アラームが鳴ったときの対応

1. CloudWatch Logs で、アラームの時刻の ERROR ログを見る（リクエスト ID でたどる）
2. ECS のタスクが止まっている場合は、サービスのイベントとタスクの停止理由を見る
3. 原因が設定の誤りなら直して `aws-up` をやり直す。アプリの不具合なら Issue を登録して直す
4. 発表中などで急ぐ場合は、直前に動いていたイメージに戻す（ECR に残っているイメージを指定して再デプロイする）

## バックアップ

| 対象 | 方法 |
| --- | --- |
| DB（RDS） | 環境がある間は、RDS の自動バックアップ（保存 1 日）を使う。`aws-down` で環境を消す前に、最終スナップショットを取る。次の `aws-up` で、そこから復元するかを選べる。古いスナップショットは最新の 2 つだけ残す |
| 画像（S3） | `aws-down` のときに、残すか消すかを選ぶ。残す場合はバケットを消さずに次の環境でも使う |
| ローカルの開発データ | 保証しない（`docker compose down -v` で消える） |

スナップショットからの復元は、発表の前に 1 回試して手順を確かめておく。
