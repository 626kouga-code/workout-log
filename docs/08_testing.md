# テスト方針

[目次に戻る](README.md)

PR ごとに GitHub Actions でテストを流し、失敗したらマージしない（[CI/CD](09_ci-cd.md)）。

## テストの種類

| 種類 | 道具 | 主な対象 |
| --- | --- | --- |
| 単体テスト | Vitest | 計算や判定のロジック（DB を使わない） |
| 結合テスト | Vitest ＋ MySQL（Docker） | `src/server/` のサービス関数、Route Handlers（DB を使う） |
| 画面のテスト | Vitest ＋ Testing Library（jsdom） | 部品・画面の振る舞い |
| E2E テスト | Playwright | ブラウザで、利用者の操作の流れを通して確かめる |

### 単体テスト

- 推定 1RM（Epley 式、1 回のとき、13 回以上を除外する。F-31）
- 自己ベストの判定（最大重量・推定 1RM・重量ごとの最大回数・時間種目の最長時間。初めての記録は数えない。F-32, F-33）
- 週の区切り・「実施日」の日本時間での扱い（日付が変わる 0 時前後の境界値）
- 体重の 7 日間の移動平均（F-41）
- Zod の入力スキーマ（境界値：重量 999.75kg、本文 280 文字、ユーザーIDの文字種など）
- 同期の競合の解決（後に変更したほうを採用する、削除されたものへの更新を無視する。06 の[記録中のデータの同期](06_api.md#記録中のデータの同期)）
- 端末側の送信待ちキュー（追加した順に送る、送れた分だけ消す、失敗したら残す）

### 結合テスト

本物の MySQL（`docker compose` で起動したもの、CI ではサービスコンテナ）に、テスト用のデータベースを作って流す。テストごとにデータを消して、互いに影響しないようにする。

- **認可**：他人のワークアウト・メニュー・体重を、取得・変更・削除できないこと（存在を知らせないよう 404 になること）
- **メール未確認**：未確認のユーザーが投稿・コメント・いいね・フォローをするとエラーになること（F-02）
- **同期**（`POST /api/workouts/sync`）：同じ変更を 2 回送っても 1 回しか反映されないこと、複数の端末からの変更の競合、記録中のワークアウトが 1 件に保たれること
- **退会**（F-06）：本人のデータがすべて消えること、返信が付いたコメントが「削除されたユーザー」として残ること、他人のデータは残ること
- **集計の性能**：1 ユーザーに 3 年分（約 500 ワークアウト、2 万セット）を入れ、グラフ・自己ベストの集計が 1 秒以内に返ること（非機能要件）
- **タイムライン**：フォロー中のユーザーだけが出ること、カーソルで続きが重複・欠落なく取れること

### 画面のテスト

- 記録画面：前回の値が初期表示されること、セットの複製、±2.5kg ボタン、「未送信 n 件」の表示
- インターバルタイマー：偽の時計（Vitest の fake timers）で、残り時間・±15 秒・終了時の通知を確かめる。画面を離れて戻ったときも、開始時刻から正しく残り時間を出すこと
- PR バッジ：自己ベストの種類ごとの表示

### E2E テスト

Playwright で、本番ビルド（`next build` ＋ `next start`）に対して流す。MySQL・S3Mock・Mailpit を起動しておく。スマートフォン（iPhone 相当の画面サイズ）と PC の 2 つの画面サイズで流す。

| シナリオ | 内容 |
| --- | --- |
| 登録とメール確認 | 新規登録 → Mailpit の API で確認メールのリンクを取り出して開く → SNS の操作ができるようになる |
| 記録と自己ベスト | メニューを作る → メニューから開始 → セットを入力・完了 → 休憩タイマーが始まる → 自己ベストを更新して PR バッジが出る → 終了 |
| **圏外での記録** | 記録中に `context.setOffline(true)` で通信を切る → セットを入力する（「未送信」が増える） → 通信を戻す → 自動で送信され、再読み込みしても記録が残っている |
| 投稿と交流 | ワークアウトを添付して画像付きで投稿 → 別のユーザーでフォロー・いいね・コメント → 投稿者に通知と未読バッジが出る |
| 進捗と体重 | 種目別グラフ・自己ベスト一覧の表示、体重の記録と目標線 |
| 退会 | パスワードを入力して退会 → ログインできなくなり、投稿が消える |

## テストデータ

- ユーザー・ワークアウト・投稿などを作る共通の関数（fixtures）を用意し、各テストはそれを使って必要なデータだけを作る
- プリセット種目は、マイグレーションのシードと同じものを使う

## 対象外

- 負荷をかけるパフォーマンステストは MVP では行わない（利用者が数十人のため）。集計の性能は結合テストで確かめる
- 実機（iPhone・Android）での確認は、AWS に環境を作ったときに手作業で行う（ホーム画面への追加、振動、画面スリープの防止）
